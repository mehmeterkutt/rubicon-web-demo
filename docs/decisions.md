The demo's counterpart of section 15 of the SDK plan: implementation details a reader would wonder
about, one row each. Design questions (what the SDK or the fake backend's contract does, what the
user must install or run, what the demo must show) are the user's and are not decided here.

| 2026-10-15 | 9.1 | The CORS answer (Web HTTP 4) | `Access-Control-Allow-Origin: *` and `Access-Control-Expose-Headers: ETag, Retry-After, X-Request-Id` on every response that is not a preflight: 2xx, 304, the forced statuses, 400 for an unreadable body or a bad control value, 404, the redirect, and the standard library's own errors (`send_error` is overridden, so an unknown method's 501 carries them too). The preflight of a `/v1/` path answers 204 with `Allow-Methods: POST, GET`, `Allow-Headers` the fixed list `Authorization, Content-Type, Content-Encoding, If-None-Match` and `Max-Age: 7200`, never a reflection of `Access-Control-Request-Headers`, as the SDK's `TestServer` does (SDK plan section 15, step 1.3), so a header the SDK sends that the contract does not name fails here as against a backend with that list. `/control?allow_headers=X-A,X-B` adds the names of the app's `network.headers` (header-name characters only, else 400). The demo's own paths (`/control`, `/events`, `/api`) are not the contract: their preflight allows `GET, POST, PUT, DELETE` and reflects the asked headers. A preflight never takes the scripted answer (status, delay, drop, `cors=off`) and is recorded in `/requests` with the method and header names it asked for. No `Access-Control-Allow-Credentials`. |
| 2026-10-15 | 9.1 | A backend that forgets CORS | `/control?cors=off` leaves both CORS headers off every `/v1/` answer but the preflight: the gateway error page of Web HTTP 4, the SDK `TestServer`'s `omitCors`. The browser hides the answer, the SDK classifies `io` and logs `UPLOAD_FAILED_OPAQUE`, and a 429 loses its `Retry-After`. A 200 without CORS still stores the events, so the SDK's retry sends them again, as it would in the field (duplicates, never loss). `/control/reset` turns it back on. |
| 2026-10-15 | 9.1 | The User-Agent check | A `/v1/` request is expected with a mobile SDK's `rubicon-(ios\|android)/x.y.z (...)` (the iOS check, kept) or with an `Origin` header and a `User-Agent` starting `Mozilla/5.0 `, the browser's own (the web SDK sends none, Web HTTP 1). Anything else, also a `rubicon-web/...` string or a browser string without an `Origin`, is noted "unexpected User-Agent" in `/requests`. |
| 2026-10-15 | 9.1 | What the request log holds | `/requests` gains `origin` (the subdomain or tab a request came from) and the preflights; never `Referer` (Web HTTP 1 backend note) and never the key (`Bearer ***`). An unreadable batch body is noted with the exception's type, not its text. `/v1/batch` answers carry `X-Request-Id: fake-<n>`, so the exposed header reaches the SDK's DEBUG line (Android log 5.1). |
| 2026-10-15 | 9.1 | Bad control values | `status`, `delay_ms` and `since` that are not numbers, an unknown `mode` or `cors` are answered 400 and change nothing; the iOS server let the handler fail without an answer. |
| 2026-10-15 | 9.1 | Smoke run against the SDK (not part of the check) | The SDK's `dist/rubicon.min.js` (built from `rubicon-web-sdk` 67d39a0) on a page served from the loopback interface as `http://a.rubicon.localhost:9999`, `host` `http://127.0.0.1:8090`: in Playwright 1.63.0 Chromium 153.0.8010.12, Firefox 155.0 and WebKit 26.6 the preflights reached the server, the batch arrived gzip-compressed and was stored, the remote configuration was read with its ETag, and the SDK's DEBUG line showed the exposed `X-Request-Id`; no "unexpected User-Agent".
