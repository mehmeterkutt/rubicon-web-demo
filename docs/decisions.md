# Implementation decisions

The demo's counterpart of section 15 of the SDK plan: implementation details a reader would wonder
about, one row each. Design questions (what the SDK or the fake backend's contract does, what the
user must install or run, what the demo must show) are the user's and are not decided here.

| Date | Step | Question | Answer |
|---|---|---|---|
| 2026-10-15 | 9.1 | The toolchain skeleton | One package, no workspace members: `pnpm-workspace.yaml` holds only `minimumReleaseAge: 10080`, which pnpm 12.11.2 reads without a `packages` list (checked: `pnpm add -D prettier@3.9.10` is refused, `prettier@latest` resolves to 3.9.9). `.npmrc` `engine-strict=true`, `.node-version` 24, `packageManager` `pnpm@12.11.2`, as in the SDK repository. Prettier 3.9.9, the newest version at least seven days old (3.9.10 is of 2026-10-10), with the SDK's `.prettierrc.json`; Markdown is not formatted. `scripts/check.sh` runs the format check and the fake backend's tests; later steps add lint, type check, build and Playwright. |
| 2026-10-15 | 9.1 | Python version and the server's state | Standard library only, Python 3.9 or later, since the `python3` of macOS 27 is 3.9.6 (no `match`, no `X \| Y` annotations); the check verifies the version. The state the iOS server keeps in module globals (control, events, requests) lives on a `FakeBackend` instance (a `ThreadingHTTPServer`) with its own configuration directory, so each test runs its own server on port 0 with a temporary directory; the command line is unchanged (`server.py [port]`, `0.0.0.0:8080`, `fake-server/config/`, which git ignores). |
| 2026-10-15 | 9.1 | The CORS answer (Web HTTP 4) | `Access-Control-Allow-Origin: *` and `Access-Control-Expose-Headers: ETag, Retry-After, X-Request-Id` on every response that is not a preflight: 2xx, 304, the forced statuses, 400 for an unreadable body or a bad control value, 404, the redirect, and the standard library's own errors (`send_error` is overridden, so an unknown method's 501 carries them too). The preflight of a `/v1/` path answers 204 with `Allow-Methods: POST, GET`, `Allow-Headers` the fixed list `Authorization, Content-Type, Content-Encoding, If-None-Match` and `Max-Age: 7200`, never a reflection of `Access-Control-Request-Headers`, as the SDK's `TestServer` does (SDK plan section 15, step 1.3), so a header the SDK sends that the contract does not name fails here as against a backend with that list. `/control?allow_headers=X-A,X-B` adds the names of the app's `network.headers` (header-name characters only, else 400). The demo's own paths (`/control`, `/events`, `/api`) are not the contract: their preflight allows `GET, POST, PUT, DELETE` and reflects the asked headers. A preflight never takes the scripted answer (status, delay, drop, `cors=off`) and is recorded in `/requests` with the method and header names it asked for. No `Access-Control-Allow-Credentials`. |
| 2026-10-15 | 9.1 | A backend that forgets CORS | `/control?cors=off` leaves both CORS headers off every `/v1/` answer but the preflight: the gateway error page of Web HTTP 4, the SDK `TestServer`'s `omitCors`. The browser hides the answer, the SDK classifies `io` and logs `UPLOAD_FAILED_OPAQUE`, and a 429 loses its `Retry-After`. A 200 without CORS still stores the events, so the SDK's retry sends them again, as it would in the field (duplicates, never loss). `/control/reset` turns it back on. |
| 2026-10-15 | 9.1 | The User-Agent check | A `/v1/` request is expected with a mobile SDK's `rubicon-(ios\|android)/x.y.z (...)` (the iOS check, kept) or with an `Origin` header and a `User-Agent` starting `Mozilla/5.0 `, the browser's own (the web SDK sends none, Web HTTP 1). Anything else, also a `rubicon-web/...` string or a browser string without an `Origin`, is noted "unexpected User-Agent" in `/requests`. |
| 2026-10-15 | 9.1 | What the request log holds | `/requests` gains `origin` (the subdomain or tab a request came from) and the preflights; never `Referer` (Web HTTP 1 backend note) and never the key (`Bearer ***`). An unreadable batch body is noted with the exception's type, not its text. `/v1/batch` answers carry `X-Request-Id: fake-<n>`, so the exposed header reaches the SDK's DEBUG line (Android log 5.1). |
| 2026-10-15 | 9.1 | Bad control values | `status`, `delay_ms` and `since` that are not numbers, an unknown `mode` or `cors` are answered 400 and change nothing; the iOS server let the handler fail without an answer. |
| 2026-10-15 | 9.1 | Smoke run against the SDK (not part of the check) | The SDK's `dist/rubicon.min.js` (built from `rubicon-web-sdk` 67d39a0) on a page served from the loopback interface as `http://a.rubicon.localhost:9999`, `host` `http://127.0.0.1:8090`: in Playwright 1.63.0 Chromium 153.0.8010.12, Firefox 155.0 and WebKit 26.6 the preflights reached the server, the batch arrived gzip-compressed and was stored, the remote configuration was read with its ETag, and the SDK's DEBUG line showed the exposed `X-Request-Id`; no "unexpected User-Agent". A page fulfilled through Playwright's `page.route` instead got no request from Chromium through to `127.0.0.1` (not even the preflight; Firefox and WebKit were unaffected; cause not investigated, probably Chromium's local network rules for a page with no address), so the demo's Playwright suite serves real pages. |
| 2026-10-15 | 9.1 | The two hostnames of D15 in the user's own browser (answered by the user) | Manual runs use the D15 names `a.rubicon.test` and `b.rubicon.test` through one line the user adds to `/etc/hosts`, `127.0.0.1 a.rubicon.test b.rubicon.test` (README, Hostnames); Playwright keeps D15's per-engine settings (a Chromium resolver rule, a Firefox preference, a proxy in WebKit) and needs no machine change. `*.localhost` is documented in the README as the zero-setup fallback, with the Safari caveat. Rejected: `a.rubicon.localhost` and `b.rubicon.localhost` as the main way (other names than D15's, and WebKit and Safari accept `Domain=localhost`, so the identity cookie would be visible to every `*.localhost` site and the subdomain check would mislead in Safari); public wildcard DNS such as `localtest.me` or `nip.io` (someone else's service, blocked by some routers, and no resolution offline, which breaks the offline scenarios). The probe behind the answer, on 2026-10-15 with Playwright 1.63.0 (Chromium 153.0.8010.12, Firefox 155.0, WebKit 26.6) and real Safari 27.0.1 on macOS 27: a page on host a discovers the cookie domain as the SDK does (from the last label up), sets a domain and a host-only cookie and moves to host b. `rubicon.test` (with the D15 settings): domain `rubicon.test` in all three engines, b sees the domain cookie only. `rubicon.localhost` (no setup): Chromium and Firefox choose `rubicon.localhost`, WebKit and Safari `localhost`; b sees the domain cookie in all four; `isSecureContext` is true. `localtest.me`: works, domain `localtest.me`. Serving the app on these names belongs to step 9.2. | `README.md` (Hostnames) |
| 2026-10-15 | 9.1 | The fake backend's extra controls (answered by the user) | Accepted as built: `/control?cors=off`, `/control?allow_headers=`, `X-Request-Id` on batch answers, `origin` and the preflights in `/requests`, 400 for bad control values (the rows above). | - |
| 2026-10-15 | 9.1 | SDK follow-up: the cookie domain on `*.localhost` (answered by the user) | On a host such as `a.rubicon.localhost`, WebKit and Safari keep a probe cookie with `Domain=localhost`, so the SDK's discovery (`CookieDomain` in `packages/core/src/storage/cookie-domain.ts`) would choose `localhost`, wider than the site; Chromium and Firefox refuse it and choose `rubicon.localhost` (the probe in the hostnames row). The fix goes to the SDK in its next branch: `isLocalHost` also matches `*.localhost`. Nothing is changed in the SDK from this repository. | - |
